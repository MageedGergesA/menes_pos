## The original RC5 sequence

RC5 measured on the pilot runtime:

```
A 200  →  B boots  →  A 401  →  B 200
```

RC6, canonical endpoint `:8090`:

```
A boots            -> 200
B boots            -> 200
A AFTER B booted   -> 200     ← RC5 gave 401 here
B                  -> 200
distinct tokens: YES
```

**Result: `A200 → B boot → A200 → B200`. The hard blocker is cleared.**

## Reload isolation

```
A reload -> A=200  B=200
B reload -> B=200  A=200
```

Each client rotates only its own secret; neither reload disturbs the other.

## Register + Floor collision

RC6 investigation found the Floor had *also* reused the config-keyed row, so
Register-vs-Register alone would not have proved the fix. Both directions were tested:

```
Register C + Floor D  ->  C=200  D=200
Floor E + Register F  ->  E=200  F=200
```

## Cookie contract

Observed `Set-Cookie` on a first Register open with a fresh jar:

```
Set-Cookie: mezze_rid=956tW5lWJ23Z; Expires=Thu, 12 Aug 2027 07:36:49 GMT;
            HttpOnly; Path=/mezze; SameSite=Lax
```

| Property | Result |
|---|---|
| Server-issued | **YES** — generated by `secrets`, never client-invented |
| Distinct per client | **DISTINCT** (A rid ≠ B rid) |
| HttpOnly | **YES** |
| Path | `/mezze` |
| SameSite | `Lax` |
| **Authenticates on its own** | **NO — 401.** Sent as a bearer token it is rejected |

The locator is a *locator*. Presenting one never returns an existing token — the server
always mints a fresh secret — and the page route is `auth='user'`, so an anonymous caller
cannot mint anything. No bearer secret was moved into browser storage.

## 4-worker concurrency

The pilot runs 4 workers, so this was proved on the real multi-process runtime rather than
in single-process test mode:

```
A: 25/25 at 200
B: 25/25 at 200
```

From the server log, **4 distinct worker PIDs** served those requests
(`1179464`, `1179465`, `1179467`, `1179469`), 62 of 63 calls at 200 — the single non-200
is the deliberate "locator as token" 401. **No process-local token state is required.**

## Scoped revocation

Performed on a disposable instance, not on an operator credential:

```
revoke A (cashier-web-1-x6iR61rLLCSS)
A -> 403   (TERMINAL_REVOKED)
B -> 200
```

**403, not 401, is correct and unchanged.** The existing contract treats a resolvable but
revoked terminal as an *authorization* denial; only an unknown/absent credential is 401.
RC6 did not alter that mapping. The disposable instance was re-activated afterwards and the
test rows were later removed.

## Restart recovery

```
before restart:              A=200  B=200
after restart, SAME tokens:  A=200  B=200      ← DB-persisted, not process-local
A re-bootstraps:             A=200  B-still=200
B re-bootstraps:             B=200  A-still=200
```

Identity after restart remained `mezze-v1.0-rc6` / `e85be35c…` / `1.0.0-rc.6` /
`19.0.2.7.0`.

| Case | Result |

per-instance rows coexist with them under the existing UNIQUE constraint — no collision, no
migration, no destroyed data.
