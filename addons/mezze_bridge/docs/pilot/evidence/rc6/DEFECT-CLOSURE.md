## DEFECT-01 — concurrent Register sessions evicted each other

### Root cause, which had two layers

**Layer 1 — identity.** Both `cashier.py::_mint_terminal_token` and
`floor.py::_floor_mint_token` resolved their `mezze.terminal` by
`cashier-web-<pos_config_id>`. A `pos.config` is *configuration* identity, not
*client-session* identity, so every browser on that config found the same row. Worse than
RC5 recorded: the Floor deliberately reused the Register's row, so opening the **Floor**
evicted another device's **Register** too.

**Layer 2 — rotation.** `mezze.terminal` already ships `rotate_token()` with a bounded
grace window (`prev_token_fingerprint`, accepted by `_resolve_principal`). Both
controllers bypassed it with a raw `write({'token': ...})`, which replaced
`token_fingerprint` without preserving the outgoing one — so the grace window the model
implements never applied, and the evicted session died *immediately* rather than surviving
the window. Fixing only layer 1 would have left this latent.

### The fix

New helper `controllers/register_instance.py`:

* identifier becomes `cashier-web-<config_id>-<rid>`, where `rid` is an opaque
  **server-issued register-instance locator** (72 bits from `secrets`);
* `mezze.terminal.identifier` **already carries a UNIQUE constraint**, so distinct clients
  get distinct rows with **no new model, no new column and no migration** — which is why
  the module version is not bumped;
* re-opening an instance now goes through `rotate_token()`, so the outgoing key survives
  its grace window;
* a **revoked** instance stays revoked — reopening its page does not silently re-activate
  a principal an operator disabled.

### The locator is not a credential

| Property | How |
|---|---|
| Server-issued | generated by `secrets.token_urlsafe`, never invented by the browser |
| Not a secret | presenting one **never returns an existing token**; the server always mints a fresh one |
| Cannot authenticate | measured live: locator sent as a bearer token → **401** |
| Not reachable by an anonymous caller | the route is `auth='user'` |
| Not widening exposure | carried in an **HttpOnly** cookie, `Path=/mezze`, `SameSite=Lax`; **no** bearer secret was moved into `localStorage`/`sessionStorage` (guarded by `test_15`, which parses the AST so the module docstring cannot satisfy it) |

Observed on the live runtime:

```
Set-Cookie: mezze_rid=KdRly5YLe4JA; Expires=...; HttpOnly; Path=/mezze; SameSite=Lax
```

### Policy, stated rather than implied

The locator is a cookie, so it is scoped to a **browser profile**:

* two **different devices or browsers** on one POS config get independent terminals and
  never evict each other — the pilot-critical contract;
* two **tabs of the same profile** deliberately remain one physical register, and the
  rotation grace window keeps the older tab working across a reload.

### Security regression — unchanged, verified live

| Case | Result |
|---|---|
| invalid token | **401** |
| missing token | **401** |
| locator used as token | **401** |
| valid token | **200** |
| revoked terminal | **403** (`TERMINAL_REVOKED` — the pre-existing contract: revocation is an *authorization* decision, not an authentication failure) |
| `api_security` default | still **`enforce`** — locked by `test_10` |
| least privilege / branch scope | `role='terminal'`, `branch_id` preserved |

**The fix was not achieved by relaxing security.** No enforcement was disabled, no default
changed, no shared admin token exposed, no retry-on-401 loop introduced.

### Why the 590-test suite missed this

The fixtures set `mezze_bridge.api_security = 'observe'` (audit-only) while the **shipped
default is `enforce`**. Every RC6 test sets `enforce` explicitly — proving this in observe
mode would prove nothing about the product as it ships.

### Negative control

The RC5 behaviour (config-only identifier **and** raw token overwrite) was temporarily
restored and the suite re-run on a fresh database: **7 failed + 1 error**, including the
defect's exact signature —

```
AssertionError: 401 != 200 : A's Register survives B opening the Floor
AssertionError: 0 not greater than or equal to 2 : two clients => two terminal rows, got []
```

The second line is worth keeping: under RC5 behaviour the per-instance identifier pattern
matches *nothing at all*, because every client collapsed onto one row. The sabotage was
reverted and is **not** committed.

## DEFECT-02 — stale product identity

RC5 reported `product_version "1.0.0-rc.1"` on a build tagged `mezze-v1.0-rc5`.

**Audit result: one production source, not several.** `MEZZE_PRODUCT_VERSION` in
`models/productization.py` is the only definition; every other occurrence is a historical
audit/report document, left untouched because it records what was true when written. So
this was a stale value, not a duplicate-source problem, and needed no consolidation.

| | Before | After |
|---|---|---|
| Production sources | 1 | 1 |
| Value | `1.0.0-rc.1` | **`1.0.0-rc.6`** |
| Response schema | 13 fields | **13 fields, unchanged** |

### The guard that stops it recurring

`test_24_product_version_matches_the_git_tag`: whenever `HEAD` sits **exactly** on a
`mezze-v<major>.<minor>-rc<N>` tag, the constant must read `<major>.<minor>.0-rc.<N>`.
On ordinary commits there is no tag to compare against and it skips, so it never blocks
development — it bites only when a candidate is frozen, which is when it matters.

Both directions were exercised: it **failed** while the branch still sat on the RC5 tag
with the constant already advanced, and **passed** (asserting, not skipping) once HEAD sat
on the RC6 tag — so it will not false-block RC7.
